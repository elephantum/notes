Кажется, что с точки зрения DX про разработку чатбота нужно думать как про разработку веб-сервиса

Текущие веб-фреймворки стабилизировались на архитектуре:
- есть запрос, который проходит через стадии обработки
- есть стартовая фаза мидлварей
- есть тело обработки запроса
- есть финализация результата

Мне кажется, что для чатбота нужен похожий DX

То есть всякие вспомогательные штуки типа памяти, на пре/постпроцессинге должны быть мидлварью

Request, который мы передаем в пайплайн может быть контекстом запроса

Нужно обязательно дать возможность регистрировать новые компоненты и использовать их в обработке

При этом во всей системе мы хотим обеспечить констистентность и чистоту, то есть если пайплайн сломался, то мы хотим выбросить все его побочные эффекты

Юзкейс: интеграция с mem0

Мы хотим такую интеграцию как несколько частей:
- мидлварь, которая срабатывает на каждое новое сообщение пользователя
- мидлварь, которая делает постпроцессинг каждой фразы сгенерированной агентом
- компонента контекста, которая доступна в процессе отвечания для поиска по памяти

Самый сложный вопрос для меня: как чисто и типизированно добавить компоненту в контекст

Лучшее решение сейчас, которое есть в голове - это:

```python
mem: Mem0 = ctx.get_component(Mem0)
```

Возможно, это будет достаточно эргономично

Альтернатива: конструировать асессор по необходимости, но в этом случае не получится кешировать тяжелую компоненту

Идея про чатбота как приложения в FastAPI стиле выглядит интересной

```python
agent = jims.Agent()

agent.add_middeware(Mem0)

@agent.on_user_message
def on_message(ctx) -> None:
  mem = ctx.get_component(Mem0)
  last_msg = ctx.get_last_message()
  mem.search(last_msg)
  ctx.send_agent_response(...)
```
